# M1.3 - Stop 模式进入与硬件验证

## 验证目标

验证 STM32F103ZET6 能够：
1. 正常进入 Stop 模式
2. 通过 RTC Alarm 从 Stop 模式唤醒
3. 唤醒后系统时钟恢复正常
4. 持续周期性 Stop-唤醒循环

## 硬件配置

- **开发板**: 正点原子精英 STM32F103 开发板 V2
- **MCU**: STM32F103ZET6/LQFP144
- **调试接口**: ST-Link V2（JTAG 4-pin）
- **指示灯**: LED0（STATUS_LED，PB5）- **低有效**（RESET=亮，SET=灭）
- **时钟源**: 
  - HSE: 8 MHz 外部晶振
  - LSE: 32.768 kHz（RTC 时钟源）
  - SYSCLK: 72 MHz（HSE × PLL9）

## 关键技术要点

### 1. LED 极性验证

**发现**: LED0 是**低有效**
- `GPIO_PIN_RESET`（低电平）→ LED **点亮**
- `GPIO_PIN_SET`（高电平）→ LED **熄灭**

这与硬件基线文档一致，M1 阶段成功验证了极性。

### 2. RTC Alarm EXTI 配置

**关键发现**: `HAL_RTC_SetAlarm_IT()` 已自动配置 EXTI Line 17
- 内部调用 `__HAL_RTC_ALARM_EXTI_ENABLE_IT()`
- 内部调用 `__HAL_RTC_ALARM_EXTI_ENABLE_RISING_EDGE()`
- 无需手动配置 EXTI

**证据**（来自 `stm32f1xx_hal_rtc.c:1263-1265`）：
```c
HAL_StatusTypeDef HAL_RTC_SetAlarm_IT(RTC_HandleTypeDef *hrtc, ...)
{
  // ...
  __HAL_RTC_ALARM_EXTI_ENABLE_IT();
  __HAL_RTC_ALARM_EXTI_ENABLE_RISING_EDGE();
  // ...
}
```

### 3. Stop 模式进入流程

```c
// 1. 确保外设停止和标志清理
HAL_GPIO_WritePin(STATUS_LED_GPIO_Port, STATUS_LED_Pin, GPIO_PIN_SET);  // 熄灭 LED

// 2. 挂起 SysTick，避免在 Stop 模式中唤醒
HAL_SuspendTick();

// 3. 进入 Stop 模式（低功耗稳压器，WFI 指令）
HAL_PWR_EnterSTOPMode(PWR_LOWPOWERREGULATOR_ON, PWR_STOPENTRY_WFI);

// 4. 从 Stop 唤醒后，HSE 和 PLL 已停止，需要重新配置系统时钟
SystemClock_Config();

// 5. 恢复 SysTick
HAL_ResumeTick();
```

### 4. RTC Alarm 时间进位处理

**关键问题**: 必须正确处理时、分、秒的进位

**错误实现**（只设置秒数，导致跨分钟边界后停止循环）：
```c
// ❌ 错误：分钟和小时固定为 0x00
sAlarm.AlarmTime.Hours = 0x00;
sAlarm.AlarmTime.Minutes = 0x00;
sAlarm.AlarmTime.Seconds = ((next_sec / 10) << 4) | (next_sec % 10);
```

**正确实现**（处理完整的时、分、秒进位）：
```c
// ✅ 正确：处理进位
s += 5;
if (s >= 60) {
  s -= 60;
  m += 1;
  if (m >= 60) {
    m -= 60;
    h += 1;
    if (h >= 24) {
      h = 0;
    }
  }
}

// 转回 BCD 格式
sAlarm.AlarmTime.Hours = ((h / 10) << 4) | (h % 10);
sAlarm.AlarmTime.Minutes = ((m / 10) << 4) | (m % 10);
sAlarm.AlarmTime.Seconds = ((s / 10) << 4) | (s % 10);
```

### 5. 调试器连接问题与解决

**问题**: Stop 模式会断开 SWD 调试连接，程序无法重新下载

**解决方案**:
1. **启动延迟窗口**（3 秒快闪 6 次）：给调试器足够连接时间
2. **物理复位方法**：按住 RESET 按钮 → 点击 Debug → 松开 RESET

**代码实现**：
```c
// 启动延迟 - 给调试器连接留出时间窗口
for (int i = 0; i < 6; i++)
{
  HAL_GPIO_TogglePin(STATUS_LED_GPIO_Port, STATUS_LED_Pin);
  HAL_Delay(500);  // 快闪 6 次 = 3 秒延迟
}
```

### 6. STM32F1 RTC 读取顺序

**重要**: 必须先读日期，再读时间，以解锁 RTC 影子寄存器

```c
HAL_RTC_GetTime(&hrtc, &sTime, RTC_FORMAT_BCD);
HAL_RTC_GetDate(&hrtc, &sDate, RTC_FORMAT_BCD);  // 必须调用，即使不使用日期
```

### 7. LSE 起振等待（Debug 模式 Error_Handler 根因）

**现象**: Run 模式（直接下载运行）完全正常，但 Debug 模式即使全速运行也进 `Error_Handler()`，
失败点在 `MX_RTC_Init()` 内部。

**根因**: CubeMX 生成的 `HAL_RTC_MspInit()` 只做时钟使能，**没有等待 LSE 起振**。
而 `HAL_RTC_Init()` → `RTC_EnterInitMode()` 需要等 RTOFF，**RTOFF 由 RTCCLK 驱动**：

```
LSE 未稳 → RTCCLK 不来 → RTOFF 永不置位 → HAL 超时 → Error_Handler()
```

Run/Debug 差异在于起振时机：Run 模式往往刚下载完或冷上电，VBAT 域已通电、LSE 多半已在振；
Debug 的 connect-under-reset 会反复拉复位、可能重新拉起振荡器，起振窗口正好撞进 HAL 超时窗内。

**手册依据**（《STM32F103 精英开发指南V1.3》）：

| 页码 | 内容 |
|------|------|
| p422 | 正点原子 `rtc_init` 用寄存器轮询等 LSE，`retry=200`、每次 `delay_ms(5)`，最长等 1 秒，超时才降级 LSI |
| p414 | 「APB1 接口刚刚被开启之后，在第一次的内部寄存器更新之前，从 APB1 上读取的 RTC 寄存器值可能被破坏了（通常读到 0）……软件首先必须等待 RTC_CRL 寄存器的 RSF 位被硬件置 1」 |
| p421-422 | 用 BKP 魔数判断，「确保时间只会设置一次，复位时不会重新设置时间」 |
| p417 | 备份数据寄存器不会被系统复位、电源复位、待机唤醒复位 |

**解决方案**（`rtc.c` 的 `USER CODE` 区，CubeMX 重新生成不丢失）：

```c
/* MspInit 0：电源时钟必须在取消备份域写保护之前使能 */
__HAL_RCC_PWR_CLK_ENABLE();

/* MspInit 1：LSE 起振等待，最长 1 秒 */
uint16_t retry = 200;
RCC->BDCR |= RCC_BDCR_LSEON;
while (retry && ((RCC->BDCR & RCC_BDCR_LSERDY) == 0U)) {
  retry--;
  HAL_Delay(5);
}
lse_ready = (retry != 0U) ? 1U : 0U;
```

**两个实现要点**：

1. **RSF 等待必须有超时上界**。RSF 同样由 RTCCLK 驱动，LSE 失败时不会置位，无界轮询会死循环。
2. **F1 上不要用 `__HAL_RTC_WRITEPROTECTION_DISABLE()` 来「解写保护」**。查
   `stm32f1xx_hal_rtc.h:354` 可见它在 F1 是 `SET_BIT(CRL, RTC_CRL_CNF)`，作用是**进入配置模式**，
   不是解锁。等 RSF 本不需要配置模式，误用会让 CNF 位残留、破坏后续所有 RTC 操作。

**LSE 失败必须显式暴露**，不静默降级（符合项目「无效数据标记」原则）：

```c
UART_Printf("[BOOT] LSE: %s\r\n", lse_ready ? "ready" : "TIMEOUT (RTC unreliable)");
```

### 8. 走时保留（BKP 魔数）

原实现每次复位都把时间拨回 `00:00:10`，周期计时被打断。按 p421 做法用 BKP_DR1 魔数
`0x5050` 标记，仅首次配置时设置时间：

```c
if (HAL_RTCEx_BKUPRead(&hrtc, RTC_BKP_DR1) != RTC_BKUP_MAGIC) {
  /* 设置时间和日期 */
  HAL_RTCEx_BKUPWrite(&hrtc, RTC_BKP_DR1, RTC_BKUP_MAGIC);
}
```

**对 M6 的影响**：本节的 LSE 起振约束在 M6 从 Stop 唤醒后恢复时钟的路径上会再次出现，
`SystemClock_Config()` 重新拉起 HSE/PLL 时同样要考虑振荡器稳定时间。

### 实际周期偏差（已修正，待 M1.4 复测）

**首次实测：标称 5 秒，实际 6 秒** —— `00:00:30 → 00:00:36 → 00:00:42`，间隔稳定 6 秒。

原因在唤醒处理顺序：`LED_Flash(3, 100)` 占约 600 ms，之后才调用
`RTC_SetNextAlarm(5)`，而它按 BCD 整秒截断计算目标值，再叠加 UART 发送等待时间。

**修正**：把 `RTC_SetNextAlarm()` 提到 LED 闪烁和日志输出**之前**，
使唤醒处理耗时不再累加到周期上，残余偏移只剩 BCD 整秒截断。

**由此引入的约束（M6 必须复核）**：alarm 目标时刻现在于处理开始时就固定，
若「唤醒处理总耗时」超过「到下次 alarm 的剩余时间」，alarm 会在处理途中到期。
此时中断置位 `alarm_triggered`，下一轮循环立即处理 —— 表现为**丢一个周期**，
不会死锁。当前 5 秒间隔 / 约 650 ms 处理耗时余量充足，
但 M6 缩短周期或延长采集时必须重新核算：

```
唤醒处理总耗时（采集 + 处理 + 上报） < 周期 - BCD 截断误差(≤1s)
```

M6 门禁「周期大于一次最坏采集、处理和上报总时长」正对应此式，
且必须按**实测周期**取值，不能用标称值。

### 调试器自动退出说明

Debug 模式下调试会话在首次进入 Stop 后自动断开，**这是预期行为、不是故障**：
Stop 模式关闭 HSE/PLL，SWD 接口失去时钟，调试器必然掉线。

此现象与第 7 节的 `Error_Handler` 问题是两件独立的事 —— 前者一直会发生，
后者是 LSE 起振缺等待导致，已修复。

## 参考例程与本项目适配边界

本验证参考正点原子资料盘中的：

- `实验15 RTC实验/Drivers/BSP/RTC/rtc.c`：LSE 起振轮询、LSI 降级、BKP 时钟源标记、F1 RTC 计数器直接寄存器设置；
- `实验16 低功耗实验/实验16-3 停止模式实验/Drivers/BSP/PWR/pwr.c`：`HAL_PWR_EnterSTOPMode(PWR_LOWPOWERREGULATOR_ON, PWR_STOPENTRY_WFI)` 的 Stop 进入方式。

本项目与例程的差异：

- 例程用按键作为唤醒源，本项目用 RTC Alarm 经 EXTI Line 17 唤醒；
- 例程的 RTC 中断中有演示性打印，本项目中断只递增计数并置位标志，日志在主循环输出；
- 例程唤醒后重新初始化 72 MHz 系统时钟，本项目保留该原则，但不再让普通 `SystemClock_Config()` 固定覆盖 RTC 的 LSE/LSI 选择。
