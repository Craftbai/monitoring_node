# 开发路线图

本文档回答“项目从哪里开始、按什么顺序做到可演示”。需求范围由[需求与边界](01_需求与边界.md)约束，模块交互由[任务与数据流](02_任务与数据流.md)定义，每阶段是否通过由[验证清单](04_验证清单.md)判断。

## 1. 推进原则

- 按 M0 到 M7 顺序推进，当前阶段门禁未满足时，不同时接入全部硬件和 RTOS 功能。
- 先保存可复现的单模块证据，再做模块集成。
- 算法先在 PC 浮点参考上建立真值，再移植 CMSIS-DSP/Q15。
- 低功耗最后集成但最早验证最小 Stop 唤醒，避免完成功能后才发现板级漏电或时钟恢复问题。
- 每个“已完成”都要注明验证层级：静态文档、PC 仿真、目标板、真实传感器或整机长稳。

## 2. 阶段总览

| 阶段 | 目标 | 主要交付物 | 退出门禁 |
| --- | --- | --- | --- |
| M0 基线冻结 | 固定正点原子精英板 V2 / STM32F103ZET6，并确认传感器、前端、工具链和上报方式 | `hardware/硬件基线.md`、数据手册链接、引脚表 | 关键硬件项无“待确认” |
| M1 板级冒烟 | 跑通最小 MCU 工程和调试链 | CubeIDE 工程、构建记录、UART 日志 | 可下载、复位、打印、RTC 唤醒、进入/退出 Stop |
| M2 单设备驱动 | 分别证明 SPI、I2C、ADC DMA 可用 | 三个最小驱动测试、原始数据 | ID/读数/超时/恢复路径可复现 |
| M3 PC 算法参考 | 固定数据格式、特征公式和期望值 | Python 脚本、CSV 样本、测试 | 浮点结果和边界用例稳定 |
| M4 采集与 DSP | 建立固定窗口和 CMSIS-DSP 结果 | 块池、采集任务、Q15/浮点对照 | 无覆盖丢块，误差和饱和可解释 |
| M5 RTOS 闭环 | 接通状态机、告警、上报和健康监测 | 任务、队列、告警状态机、结构化结果 | 正常与故障周期均能收尾 |
| M6 低功耗闭环 | 完成周期唤醒、采集、上报和 Stop | 功耗状态记录、唤醒恢复测试 | 多周期稳定且实测功耗有证据 |
| M7 整机验收 | 在安全演示对象上完成场景与长稳 | 演示记录、异常矩阵、版本清单 | 验证清单通过，结论边界明确 |

## 3. M0：先冻结真实基线

1. 在 [`hardware/硬件基线.md`](../hardware/硬件基线.md) 中记录正点原子精英 STM32F103 开发板 V2，并通过芯片 ID 和工程器件信息确认 STM32F103ZET6/LQFP144。
2. 填写 512 KB Flash、64 KB SRAM、调试器、供电方式和可测电流路径，并以官方数据手册和实际链接映射为最终依据。
3. 填写振动、温度、电流前端的完整型号、接口、电压、量程、带宽和数据手册版本。
4. 确认振动采样率能覆盖目标频段；确认传感器 FIFO、SPI 吞吐和唤醒时间满足窗口采集。
5. 确认电流前端仅连接安全低压对象，并明确 ADC 输入最大值、偏置、比例和保护。
6. 确认首版上报方式只选 UART 或一个具体无线模块。
7. 记录 STM32CubeIDE、CubeMX、固件包、FreeRTOS/CMSIS-DSP 和 ST-Link 版本。

硬件未到位时可并行完成配置检查、CSV 格式、PC 算法参考和状态机单元测试，但不能把这些结果标记为目标板通过。

## 4. M1：建立最小板级冒烟工程

CubeMX 首次配置只打开为基础验证必需的功能：

1. 时钟和调试接口。
2. 一个 UART 日志口。
3. RTC 周期唤醒。
4. 一个 LED 或测试 GPIO。
5. FreeRTOS 可在确认裸机外设与低功耗后加入，避免同时排查调度和板级问题。

最小验证顺序为：构建 -> 下载 -> 读取芯片 ID/版本 -> UART 输出启动原因 -> LED 心跳 -> RTC 唤醒 -> Stop 前后 GPIO 翻转。用逻辑分析仪或示波器确认实际休眠区间；不要仅凭串口日志判断已经进入 Stop。

退出 M1 前保存：工程配置、完整构建命令或 IDE 版本、下载日志、启动串口日志、Stop 唤醒波形和测试日期。

## 5. M2：逐个跑通设备

### 5.1 振动通道

- 读取 `WHO_AM_I` 或等价器件标识。
- 配置量程、输出数据率、带宽、FIFO 和中断。
- 采集静止、轻敲和风扇运行三组原始数据。
- 验证 SPI 超时、错误 ID、FIFO 溢出和器件复位。

### 5.2 温度通道

- 验证器件地址、转换时间、分辨率和单位换算。
- 与可信温度计做至少两个温度点的合理性对照。
- 验证设备断开、总线忙和 I2C 恢复路径。

### 5.3 电流通道

- 先测模拟前端零点和满量程安全范围，再连接 ADC。
- 用已知负载或仪表完成两点以上标定。
- 验证 ADC 触发源、DMA 半/全缓冲、溢出和采样时间。
- 保存原始 ADC 码值、参考仪表读数和换算参数。

三个通道应先用独立小程序验证，不在这一阶段引入 FFT、告警和无线通信。

## 6. M3：建立 PC 侧算法真值

1. 定义 CSV 列：`timestamp_s`、三轴加速度或选定轴、`temperature_c`、`current_a`、场景标签。
2. 保存正常、轻微异常、持续异常和无效/饱和样本。
3. 用 NumPy/SciPy 实现去直流、窗函数、RMS、峰峰值、峰值因子和频带能量。
4. 对零输入、常量、单频正弦、冲击、截幅和缺样分别建立期望结果。
5. 明确 FFT 归一化、单边谱倍增、窗增益和频带端点规则。
6. 用 `pytest` 固化结果，避免 MCU 移植时边算边改定义。

当前仓库仅包含 Python 依赖清单，还没有算法脚本或样本；完成此阶段后才能声称 PC 侧算法已验证。

## 7. M4：采集链与 CMSIS-DSP

1. 实现固定大小采样块和静态块池。
2. DMA/FIFO 回调只提交块索引，处理任务取得所有权。
3. 检查块序号、采样时间、丢块和饱和标志。
4. 将 PC 浮点参考逐项移植到 CMSIS-DSP；先浮点，再根据性能与资源证据决定是否使用 Q15。
5. 用完全相同的原始样本对照 PC 与 MCU 输出。
6. 记录处理耗时、栈高水位、块池峰值占用和误差。

若浮点实现已经满足截止时间和功耗，不应仅为展示技术而强制改成 Q15。选择定点必须有资源或性能依据。

## 8. M5：建立 FreeRTOS 周期闭环

1. 创建 `acquisition_task`、`processing_task`、`cycle_task`、`report_task` 和 `health_task`。
2. 先接 UART 结构化输出，固定周期结果字段。
3. 实现 `NORMAL/PENDING/ACTIVE/RECOVERING` 告警状态机和迟滞。
4. 为采集超时、传感器断开、块池耗尽、算法无效和上报超时注入故障。
5. 看门狗只在关键任务心跳、周期状态和队列健康均满足时喂狗。
6. 确认每个周期无论成功或失败都能到达明确的收尾状态。

## 9. M6：集成低功耗

1. 记录运行、采集、处理、上报和 Stop 五种状态的电流与持续时间。
2. 逐项关闭不用的 GPIO、总线、传感器和调试功能，确认漏电来源。
3. 验证从 Stop 唤醒后的系统时钟、HAL 时基、UART、I2C、SPI、ADC DMA 和 RTOS 时间行为。
4. 连续运行至少 100 个周期作为初始稳定性检查，再根据目标周期扩展时长。
5. 计算整周期平均电流与预计续航，公式、仪器、供电电压和采样设置一并保存。

“成功进入 Stop”与“整机低功耗达标”是两个不同结论，后者必须包含板卡、传感器和上报模块的实测。

## 10. M7：整机演示与证据

至少准备以下场景：

| 场景 | 输入 | 预期结果 |
| --- | --- | --- |
| 正常运行 | 风扇稳定、温度和电流正常 | 特征有效、告警保持 `NORMAL` |
| 振动异常 | 可控偏心或松动模拟 | 连续确认后进入 `ACTIVE` |
| 温度超限 | 安全可控的温升模拟 | 温度告警触发，其他通道仍有独立状态 |
| 传感器断开 | 断开一个低压传感器 | 该通道无效并报告错误，不输出虚假正常 |
| 上报失败 | 断开 UART 接收端或模拟通信超时 | 周期记录失败并按截止时间进入收尾 |
| RTC 多周期 | 连续唤醒、采集、上报和休眠 | `cycle_id` 连续、无死锁、功耗波形可解释 |

## 11. 第一次开工建议

在 ZET6 开发板方向已确定但传感器尚未冻结时，先完成这四项：

1. 复核硬件基线中的精英板 V2 修订、跳线位置、引脚候选项和待确认项。
2. 安装并记录 STM32CubeIDE、CubeMX、ST-Link 和 Python 版本。
3. 用配置样例确定首个振动窗口的采样率、点数和目标频带是否自洽。
4. 准备一份合成正弦波 CSV，开始 PC 侧 RMS 与 FFT 参考测试。

开发板确认后的第一个真机目标只有一个：稳定完成“启动日志 -> RTC 唤醒 -> Stop -> 再次输出日志”。之后再接第一个传感器；传感器引脚仍需在 M0 中单独冻结。

## 12. 变更控制

- 范围和安全边界变化先修改 01。
- 分层、任务、状态、数据对象和错误恢复变化只在 02 定义。
- 硬件选择、工具和测量仪器变化只在 03 与硬件基线维护。
- 阶段顺序和退出门禁变化只在 05 维护。
- 测试结果和完成状态只在 04 或独立证据记录中维护，计划文本不代表实现。
